# GC Wrapped

Group chat analytics platform: chat exports → Postgres warehouse (dbt) → LLM enrichment → RAG Q&A with citations → "Wrapped" profile per member. Resume project for Ryan Phan (new-grad SWE / data eng). Planning happens in a separate claude.ai project; this file is what you need to work in the repo.

## Every session
Context is cleared after every session. Anything not written into the repo is lost, so write it down.
1. Read `docs/STATUS.md` (where things stand) and skim `docs/decisions.md` (why things are the way they are).
2. Ryan pastes a session brief. Do that task only.

## Git and CI
- Never merge a PR unless every check on its latest commit is green. If a check fails for an infrastructure reason, re-run it or push an empty commit; never merge around it.
- main is protected: all changes go through a PR, including STATUS.md hash updates.

## Current phase
Phase 1 — Pipeline: parse one platform's export → clean/dedupe → Postgres `raw` schema → dbt models (messages, member activity, reply times, threads, activity over time) with tests → Airflow landing-zone DAG → simple dashboard.
Done when: a fresh export runs end to end with one command and all tests pass.
Source platform: Instagram DMs (Meta "Download your information" export, JSON format). Messenger and TikTok are possible later platforms; iMessage is out (no Mac).
NOT in Phase 1: LLM calls, embeddings, analysis of image/video content, React frontend, deploy, a second platform.

## Privacy rules (hard requirements)
- You are a third-party API. Real chat data must never enter your context.
- Never read, print, grep, list contents of, or open anything under `data/`. Never read, list, or search anything outside this repo; real chat exports live elsewhere and you must never access them.
- All test data is synthetic: use only fixtures in `tests/fixtures/`, generated by `tests/synthetic/instagram.py` (`make synth`). Never ask for or accept pasted real messages.
- Never read or reference `~/gcw-private`, any `real.env`, or the `gc-wrapped-real` compose project. Never run make real-ingest or any command with a non-.env ENV_FILE; real-ingest is verified only by the real-ingest-synthetic CI job. Tests that exercise the refusal path through subprocess are fine. Host-side settings load only the file named by ENV_FILE.
- Only connect to the `gcw_dev` database (synthetic data). Never run psql, dbt, or scripts against `gcw_real`.
- Ryan runs real-data commands in his own terminal and reports aggregate numbers. Never ask him to paste real messages, names, or output containing them.
- Unhandled CLI errors print `gcw: failed: <ExceptionTypeName>` only. `GCW_TRACEBACK=1` re-raises for the full traceback: dev only; never set on real-data runs.
- Logs and error messages never include message bodies, sender names, phone numbers, or emails. Log counts, IDs, durations, file hashes.
- Never commit chat data, media, `.env*`, or `members.yaml`. `data/` stays in `.gitignore`.
- Ingestion is deny-by-default: it loads only threads whose numeric ID is in `GCW_THREAD_ALLOWLIST` and fails if that is unset or empty. Never add a bypass (no "synthetic mode" switch, no flag, no default that skips it); dev `.env`, `.env.example` and CI list the synthetic thread IDs explicitly.
- No external API calls from pipeline code in Phase 1.
- The Instagram format spec is `docs/formats/instagram-schema.md`. Build against it, not against assumptions.

## Stack
Python 3.12 (uv), psycopg 3, pydantic-settings, Postgres 17 + pgvector (Docker), dbt-postgres, Airflow (LocalExecutor, runs from its own image: official base plus gcwrapped and dbt in an isolated venv), Streamlit dashboard, pytest, ruff, mypy --strict, GitHub Actions.

## Conventions
- Business logic lives in `src/gcwrapped/`; DAGs only call it. Everything runs and tests without Airflow.
- Type everything; `mypy --strict` passes. Config comes from env via `config.py`, never hardcoded.
- Every new behavior gets a test. Parser fixtures cover edge cases deliberately.
- Ingestion is idempotent: re-loading the same file inserts 0 rows (dedup key design is in decisions.md).
- Small diffs. Prefer boring, widely used libraries; justify any new dependency in decisions.md.

## Workflow rules
- Commit only after `make lint test` exits 0, chained with `&&`; never chain a commit after tests with `;`.

## Session rules

### Briefs and deviations
- Session briefs are written in a planning chat that cannot see this repo. File names, paths, and helper names in a brief may be wrong.
- For factual mismatches, adapt minimally and record each one under "Deviations from brief" in docs/STATUS.md.
- Stop and ask (end the session without opening a PR and state the question) only if:
  1. the brief doesn't answer a design question;
  2. a change would alter a table or dbt model schema, an API route shape, or a make-target interface beyond what the brief specifies;
  3. you would delete files the brief didn't mention;
  4. a change would touch .claude/settings.json or the redaction, consent, or allowlist code beyond what the brief specifies;
  5. the acceptance criteria can't be met as written.
- Otherwise, don't wait for plan approval: state a plan in 10 lines or fewer and proceed.
- When docs and code disagree, the code and test runs win. Fix the doc.

### Testing
- Mock only external boundaries (LLM APIs, network calls, third-party services, external binaries such as dbt). Never mock the logic under test.
- The test-isolation guard (tests/conftest.py, tests/isolation_guard.py, tests/test_isolation_guard.py) must never be weakened, skipped, or marked xfail.

### Session end (in this order)
1. Stop any dev-stack containers or processes you started (docker compose down for the dev project only).
2. Never run docker compose against the real project (COMPOSE_PROJECT_NAME=gc-wrapped-real) or with ENV_FILE pointing at real.env.
3. Overwrite docs/STATUS.md in the format below.
4. Append new decisions to docs/decisions.md.
5. Run make lint test, then create a branch, commit, push, and open a PR with gh. If the brief says to update an existing PR, push to that PR's branch instead of opening a new one.

### docs/STATUS.md format (overwrite every session, max 40 lines)
Sections, in this order:
- Phase & state (1-2 lines, plus the phase checklist if one exists)
- Done this session (grouped by file)
- Deviations from brief (or "none")
- Checks: lint, tests, dbt tests, each with pass/fail and count, plus any other value measured this session with its exact source
- Not verified: what Ryan should run or check, including any real-data make target
- Open issues (file:line) and open questions for planning
- Suggested next session

### Numbers and decisions
- Measured numbers (test and model counts, runtimes, eval scores, latency, cost) appear only in METRICS.md and the current docs/STATUS.md. Other docs, including this file, link to METRICS.md instead of stating numbers.
- Every METRICS.md row has a date and commit SHA, plus model and dataset version for eval results. Add new rows; never edit or delete an existing row. Never round up or estimate.
- docs/decisions.md is append-only. Each entry has an ID and date in its header ("## D<n> — <YYYY-MM-DD> — <title>"). To revise a decision, add a new entry that says "Supersedes D<n>"; never edit an old entry.
